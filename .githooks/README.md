# push の関門（pre-push フック）

`git push` のたびに、恒久ルール11の条件を機械で確かめる。覚えて守る運用ではなく、
**条件を満たさなければ push が止まる**形にしたもの。

## 見ているもの

引っかかれば push を止める。順番は速いものから。

| # | 見るもの | 止める条件 |
|---|---|---|
| 1 | fast-forward か | リモートの先端が、送ろうとしている履歴に含まれていない（`--force` 相当） |
| 2 | 作業ツリー | 追跡中ファイルに未コミットの変更がある／`.gitignore` されていない未追跡ファイルがある |
| 3 | `npm run test:verify` | 総合 NG |

- **`.gitignore` 済みのファイル（`output/` など）では止まらない。** `git status --porcelain` の
  既定の範囲をそのまま使っている。
- **`--force` は「フラグ」ではなく「効果」で見る。** fast-forward になる `--force` は普通の
  push と区別できないが、それは無害。逆にフラグを付けなくても非fast-forward なら止まる。
- **リモートの先端を手元に持っていないときは止める。** 「判定できない」を「問題なし」と
  扱わないため。`git fetch` してから push し直す。
- **新しいブランチの初回 push** は、比べる先が無いので fast-forward の判定をしない（止めない）。
- **ブランチの削除**（`git push --delete` 等）は、送られるコードが無いので
  作業ツリーと `test:verify` の検査を省略して通す。削除が含まれることは画面に出す。

## 作業ツリーを見る理由

`npm run test:verify` は**作業ツリーの実ファイル**を見る（`tests/visual/run-verify.mjs` の
冒頭にそう書いてある）。一方 push が送るのは HEAD。
汚れたまま検査を通しても、**その結果は push される内容を説明していない**ので止める。

## 有効になる仕組み

```
git config core.hooksPath .githooks
```

`core.hooksPath` は**ローカル設定なので追跡されない**。clone し直すと外れる。
`package.json` の `prepare` に入れてあるので、`npm install` すると自動で設定される。

外れていないかは **`npm run test:verify` の §9** が毎回見る。
**§9 が落ちたら、それは関門が外れているということなので放置しない。**

Windows では Git が `sh` でフックを起動するので、実行権限（`chmod +x`）は要らない。
git 上は `100644` のままで動く（2026-09-16 に実測）。

## 効いているかを確かめる

### 日常はこれ ―― push のたびに出る1行

関門を通ると、フックが最後にこの行を出す。

```
pre-push: 関門を通過（fast-forward・作業ツリーはクリーン・test:verify 総合OK）
```

**push を報告するときは、この行をそのまま報告に含める。**
**この行が無い push は、フックが走っていない可能性がある**ので、その旨を報告すること。
わざわざ確認の操作をしなくても、毎回の push が生存確認になる、という考え方。

設定が外れていないかは、別に **`npm run test:verify` の §9** が毎回見ている。
**§9 が落ちたら関門が外れているということなので放置しない。**

### わざわざ確かめたいとき

```bash
git push --dry-run origin main
```

`--dry-run` でも**フックは走り、リモートは進まない**（2026-09-16 に実測）。

**ただし、送るものが無いと `--dry-run` でもフックは呼ばれない。**
手元がリモートと同じときは `Everything up-to-date` と出て終わり、フックの出力は何も出ない
（2026-09-16 に実測。これを「効いていない」と読み違えないこと）。
確かめられるのは**手元がリモートより進んでいるとき**だけ。

## 回避

**`git push --no-verify` でフックを丸ごと飛ばせる。**

- **自分の判断では使わない。おいもさんの明示的な指示があるときだけ。**
- **使ったら必ず報告する。** 何のために迂回したかを残す。

関門を迂回した push は、検査を通っていない内容が公開リポジトリに出るということなので、
「急いでいるから」は理由にならない。落ちた検査を直すほうが速いことがほとんど。

## フック自体を変えるとき

`.githooks/` は**ルール11(1) の「確認なしで push してよい」対象に入れていない**。
フックは関門そのもので、ここを変える push は「関門を緩める変更を、関門自身に通す」ことに
なるため、**毎回おいもさんの承認を得る**。
