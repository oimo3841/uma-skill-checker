## 1. `exam.html` への適用

**解決する問題**
`common.css` が出来た今も exam だけが独自の値を持ち続けている。放置するほど exam 側の実装が独自に育ち、適用コストが上がる。加えて **exam と Deck が同じ `indigo` を使っており、統合後は「評価して比較する画面」との区別が付かない**。

**影響範囲**
`exam.html`（2316行）のみ。`common.css` は変更しないで済む見込み。ただしアクセント色の割り当てを変えるなら Deck 側の `:root` 6行も動く。

**実装コスト：中**
`<link>` 追加・`:root` 6行・`<style>` 26ルールのトークン化・版数検証の移植で、機械的な作業としては special と同程度。ただし判断が必要な論点が10件ある（[design-change-phase2.md](design-change-phase2.md) §4 に列挙済み）。特に次の2つは先に決める必要がある。

- exam のアクセントをどうするか（Deck と同じ藍のままにするか、exam 固有の色を割り当てるか）
- exam の絞り込みボタンも `className` を丸ごと書き換える実装（`exam.html:1892` 付近）なので、提案3を先にやると共通部品を当てられる

**属するフェーズ**：exam適用

## 2. 回帰確認ハーネスをリポジトリに入れる

実際、今回この仕組みがあったからこそ「無効列の▲▼だけが有効列と同じ濃さになる」回帰を目視ではなく数値で検出できた。

## 3. `setFilter()` の `className` 全書き換えをやめる

**解決する問題**
`special.html:1230` の `setFilter()` は、絞り込みボタンの `className` を**丸ごと文字列で再代入**している。このためマークアップ側でクラスを足しても押した瞬間に消える。今回、絞り込みピルを共通部品 `.uma-pill` に寄せられなかった唯一の理由がこれで、結果として **UmaStar OCR の絞り込みだけが共通部品の外に取り残されている**（Deck 側は `.uma-pill` を使っている）。

`exam.html` にも同じ実装がある。

**影響範囲**
`special.html` の `setFilter()`（10行程度）と、絞り込みボタン3個の `class` 属性。`exam.html` にも同様の箇所。DOM構造は変わらない。

**実装コスト：小**
`btn.className = '...'` を `btn.classList.toggle('active', ...)` に変え、マークアップに `uma-pill` を足すだけ。ただし §2-2 の「JSが掴んでいるクラス」に該当する箇所なので、変更前後で挙動を確認する必要がある（提案2のハーネスがあれば自動で確認できる）。

**属するフェーズ**：コード構造（外観の統一が目的なので、機能見直しの前でも実施可能）

## 4. 人物色（青/赤）とツールアクセント（緑）の競合

**解決する問題**
UmaStar OCR は緑がアクセントだが、照合結果の統計カードは**青**（`blue-600` の数値・`blue-700` のラベル）で描かれる。これは「親Aセット＝青系統／親Bセット＝赤系統」という人物色の規則によるもので、規則自体は意味がある。しかし画面上では、最も目立つ大きな数字が緑でも藍でもない第三の色になっており、**ツールの目的を伝える色と、データの分類を示す色が同じ強さで競合している**。

Phase 1 で「要判断」に分類し、Phase 2 では値の統一（v3→v4）だけ行い、配色の役割分担には手を付けていない。

**影響範囲**
`special.html` の `renderStatGrid()` / `buildColumnMeta()` / `PERSON_STAT_META`、`HUE_HEX`。`exam.html` も同じ仕組みを持つ。

**実装コスト：中**
値の差し替えだけなら小だが、「人物色をどこまで前面に出すか」の設計判断が要る。選択肢は3つ。

1. 統計カードの数字はニュートラル（`--uma-text`）にし、人物色は小さなバッジと表の列帯だけに留める
2. 現状維持（人物色を前面に出す）とし、代わりにツールのアクセントを結果セクションでは使わない
3. 人物色そのものを、ツールのアクセントから派生させる（例：親Aセット＝アクセントの濃淡、親Bセット＝補色）

**属するフェーズ**：配置見直し

## 5. 引き出しパネルの見出しが二重

**解決する問題**
`special.html` の引き出しパネルはヘッダに「UmaSkill Deck ／ テンプレートと比較シートをここで編集できます」と表示し、その直下の iframe が読み込む `uma-skill-deck.html` も `<h1>UmaSkill Deck</h1>` とバージョン表示を出す。結果として**同じ見出しが縦に2つ並ぶ**。統合の粗が最も目に付く箇所で、パネルの縦方向を約70px消費している。

**影響範囲**
`special.html` の `.deck-drawer-header`、`uma-skill-deck.html` の `<header>`。DOM要素の非表示または削除が必要なため、今回の「DOM変更禁止」に抵触して見送った。

**実装コスト：小**
iframe 側に「埋め込みモード」を伝える手段（クエリ文字列や `postMessage`）を1つ決め、その時だけ `<header>` を隠す。ただし **Deck 単体で開いたときの見た目を壊さないこと**が条件になるので、条件分岐の入れ方を決める必要がある。

**属するフェーズ**：配置見直し

## 8. 同義クラスの二重定義を解消する

**解決する問題**
クラス名の衝突を避けるためだけに、同じ定義が2つある。

| 実体 | 定義1 | 定義2 |
|---|---|---|
| リスト行 | `.list-card`（uma-skill-deck.html） | `.usd-list-card`（core.js） |
| 半透明パネル | `.glass-card`（common.css） | `.usd-panel`（core.js） |

Phase 2 で**値は一致させた**（すべて `common.css` のトークンを見る）が、ルール自体は二重のまま。片方だけ直す事故がまだ起こりうる。

**影響範囲**
`uma-skill-deck.html`、`js/uma-skill-deck-core.js`、および両者を読み込む `special.html`。

**実装コスト：中**

**属するフェーズ**：その他（共通化）
**Phase 1 で「事故と思われる」に分類した項目**の残り。

## 9. 結果表の人物列のインライン `style` をやめる

**解決する問題**
`special.html:1062` の `HUE_HEX` はインライン `style` で色を当てている。コードには次の趣旨のコメントが残っている。

> クラスの指定だけでは優先度で負けて反映されないことがあるため、ここではインラインstyleで確実に上書きする。

これは Tailwind ユーティリティとの詳細度の敗北を回避するための措置だった。**Phase 2 で判明したカスケードレイヤーの性質（レイヤー無しの指定がユーティリティに勝つ）により、この前提はすでに成立しない。** 現在はクラスで書けば当たる。

インライン `style` のままだと、`common.css` からの上書きが `!important` なしでは不可能な唯一の箇所として残り続ける。

**影響範囲**
`special.html` の `HUE_HEX` / `renderTableHeader()` / 結果表の行生成。`exam.html` にも同種の実装がある可能性が高い。

**実装コスト：中**
`.uma-person-col--blue` のようなクラスを `common.css`（または special の `<style>`）に定義し、インライン `style` をクラス付与に変える。色数は2系統×5値と少ないが、テーブル生成部を触るため OCR 結果表示の回帰確認が必須（提案2のハーネスが効く）。

**属するフェーズ**：コード構造
**Phase 2 で「DOMを変えたくなったが我慢した」項目**。

## 10. UmaStar OCR のボタン余白8種を共通部品に寄せる

## 11. 残った孤立値 `gap: 1px` の解消

## 12. スマートフォン最適化

**解決する問題**
375px幅で確認したところ、横スクロールは発生していない（Phase 2 の下限は守られている）が、次の課題が残る。

- **照合結果の1列目**：スキル名の列が狭く、「東京レース場○」が1文字ずつ縦に折り返される。5列（スキル名＋3人＋★合計）を375pxに収めているため。変更前から同じ状態
- **★ステッパーのタップ領域**：Phase 2 で 15×12px → 16×14px に広げたが、推奨される最小タップ領域（44×44px）には遠い
- **ページ全長**：UmaStar OCR は 375px 幅で縦4080px。ステップ1〜3を1ページに積んでいるため、結果を見るまでのスクロールが長い
- **比較シート**：候補が3人を超えると横スクロールが必須になる（`sticky` 列で対処済みだが、狭い画面では見える範囲が2列程度）

**影響範囲**
両ツールの全画面。DOM構造・情報量・操作手順の変更を伴う。

**実装コスト：大**
「狭い画面で何を捨てるか」の設計から必要になる。列の折りたたみ、カード形式への切り替え、ステップのアコーディオン化など、どれも配置と操作手順の変更になる。

**属するフェーズ**：モバイル最適化

## 13. Tailwind CDN 依存の段階的な縮小

**解決する問題**
4ツールすべてが `cdnjs` の Tailwind browser 版と `unpkg` の lucide を実行時に読み込んでいる。**CDN が落ちる・ブロックされると、レイアウトが全崩壊する**。`uma-skill-deck.html` が `.hidden` を独自に宣言しているのは、まさにこの事態への保険である（Phase 2 でも残した）。

browser 版 Tailwind は「実行時にDOMを走査してCSSを生成する」仕組みで、本番配信に向いた使い方ではない。Phase 1 の実測でも、要素を差し込んだ直後に `getComputedStyle` しても値が確定しない挙動を確認している。

`common.css` を持った今、**依存を減らす現実的な足場ができた**。

**影響範囲**
全4ツール。段階的にやるなら、まず「共通部品でまかなえるユーティリティ」から減らしていく形になる。

**実装コスト：大**
一度に全部を置き換えるのは非現実的（`class` 出現数：special 264／exam 355／index 318）。現実的な選択肢は3つ。

1. Tailwind をローカルにベンダリングして固定版を配信する（CDN障害には強くなるが、実行時生成の性質は変わらない）
2. ビルド工程を入れて必要なCSSだけを事前生成する（GitHub WebUI でのコピペ運用と相性が悪い）
3. 現状維持で、`common.css` の守備範囲を少しずつ広げる（最も安全だが時間がかかる）

**属するフェーズ**：その他（運用リスク）

## 14. `index.html` の扱いを決める

**解決する問題**
`index.html`（UmaSimple OCR）は廃止予定でツール切替UIからも除外済みだが、ファイルは残っており、GitHub Pages のルート（`/`）として配信され続けている。**URLを直接知っている人には今も見えている**。今回のデザイン統一からも外したため、他ツールと外観が食い違った状態が固定される。

**影響範囲**
`index.html` と、GitHub Pages のエントリポイント。

**実装コスト：小**
